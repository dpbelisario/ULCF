1. The road in one picture

A phase is a block of work with one goal and one completion condition. The completion condition is a checklist that tells you when the phase is finished. The project has nine phases, numbered 0 to 8. Figure 1 shows them as a chain. The left column sorts the phases by the kind of work. The right column names the part of the paper that each phase feeds, that is, the part for which the phase supplies the material.

  • Learn (phases 0 and 1). You read the pages and run the demo scripts. Nothing new is created yet.
  • Reproduce (phases 2 and 3). You run the two given simulations and check their results against reference results. Each of the two simulated switches is a baseline: an existing switch with which the paper compares the proposal.
  • Create (phases 4 to 6). You design, simulate and evaluate the proposed three-stage switch. The package gives you the tasks and the conditions that a correct result must satisfy. It does not give you the method or the result.
  • Publish (phases 7 and 8). You confirm a part of the result in an experiment, and you write the paper.

The chain shows the order in which you start the phases. You may have to return to an earlier phase: for example, a simulation result of phase 5 can show that the design of phase 4 needs a change.

Sections 2 to 10 describe one phase each, always in the same five parts.

  • Goal: what you are able to do when the phase ends.
  • You start from: the pages to read and the scripts to run.
  • You produce: what must exist when the phase ends.
  • Done when: a checklist. The phase is finished when every item is true.
  • Bring to your supervisor: what you show in the meeting that closes the phase.

The phases use technical terms that you may not know yet. Each term is explained on the pages that the phase names, and the glossary lists all of them.

Key idea

A phase ends when every item of its "Done when" list is true. A planned date that has arrived does not end a phase. A script that ran without an error does not end it either.

4. Phase 2: Reproduce the two-stage ULCF switch

Table 3. Phase 2: reproduce the two-stage ULCF switch.
GoalYou can run the given simulation of the two-stage ULCF switch, you reproduce its curve of port count versus transmitter power, and you can explain every block of its transmission chain: the sequence of elements that the signal passes from the transmitter to the receiver. The port count is the number of input ports of the whole switch (page 02). This switch is the first baseline of the paper. Its second stage, which consists of wavelength-routing switches, is also the model for the middle stage of your proposal: several small couplers and EDFAs in front of ULCF AWGs. A ULCF (uniform-loss and cyclic-frequency) AWG is a type of AWG that is built for use with several input ports (page 17).
You start fromPage 21. Then the step script matlab/main/step21_two_stage_one_point.m, which simulates one operating point: one transmitter power (PTx), one size \(M\) of the space switches (dcs_input_port_num; the script calls them DC switches) and one number \(K\) of AWG input ports (ULCF_deg). Then the main script matlab/main/main_two_stage_ULCF.m, which searches over many operating points. For every \(K\) and every \(M\) it finds the required transmitter power: the lowest transmitter power at which the bit error ratio (BER) is not above the FEC limit of \(10^{-2}\). The FEC limit is the BER up to which forward error correction (FEC) still removes the errors. The reference data are in matlab/ref_data/.
You produce(1) The output of step21_two_stage_one_point at its default operating point. It prints two tables: the power after every block, and the contributions to the signal-to-noise ratio (SNR). In both tables the simulation stands next to a hand budget: the same quantity calculated with formulas instead of waveforms. The scripts call it the closed-form budget.
(2) Three more runs of this script. In each run you change one parameter of its section 1 (PTx, dcs_input_port_num or ULCF_deg), as the header of the script suggests, and you write down your prediction before you run.
(3) Two runs of main_two_stage_ULCF, with their result files in matlab/results/: one quick run with quick_flag = 1 and one full-size run with quick_flag = 0. You set quick_flag in section 1 of the script.
Done when
  • step21_two_stage_one_point prints Self-check 1 passed and Self-check 2 passed.
  • Your curve of port count versus transmitter power agrees with the reference curve within one grid step along the power axis. The grid step is the spacing of the transmitter powers that the search tries: 1 dB with quick_flag = 1 and 0.5 dB with quick_flag = 0. The script prints the comparison as the table Difference: this run - legacy code [dB]. No number in this table is further from zero than one grid step, and NaN stands at the same places in the two tables above it. NaN means that the BER limit is not reached with any power that was tried. The "legacy code" is the earlier laboratory code that produced the reference curve.
  • You can say which line of the table SNR contributions in the signal bandwidth [dB] limits the BER at low transmitter power, which line limits it at high transmitter power, and why. Among the four contributions, the one with the lowest value limits the BER.
  • You can explain why a curve with a larger \(K\) reaches the same port count at a lower transmitter power.
  • You can explain why small differences from the reference curve are expected. Page 21 and the headers of the two scripts list the reasons.
Bring to your supervisor

The figure of the run with quick_flag = 0, the table of differences, your three predictions next to the three results, and your answer to the question about the SNR table.

Table 5. Phase 4: design the proposal on paper and in integers.
GoalYou find which wavelength every connection of the proposed switch uses, and you count how many leaks in a third-stage switch fall on the wavelength of the target signal. The target signal is the one signal whose bit errors are counted. This phase needs whole numbers only: no waveform, no noise, no BER.
You start fromPage 23 and matlab/work/work1_wavelength_rule.m. This file states the task; it holds no solution. Pages 17 and 22 and the function awg_channel give you the routing of an AWG and the wiring of the conventional switch.
You produce(1) The wavelength rule: the wavelength channel of a connection from first-stage switch \(i\) to third-stage switch \(j\). Your division of the first-stage switches into \(K\) input groups, one group for each input port of the ULCF AWG, is a part of the rule. Show the rule for a small example that you can check by hand.
(2) Exact definitions of two traffic conditions, dispersed and concentrated (the task files call them traffic patterns). Roughly, the signals that pass one third-stage switch come from many input groups or from one input group. Making this exact is a part of your work.
(3) For both traffic conditions: the number of leaks on the wavelength of the target signal in one third-stage switch, for several \(K\) and \(M\), as a table or a figure.

The "Done when" lists of phases 4 to 6 consist of consistency conditions. A consistency condition is a property that a correct result must have, whatever the result is. It tests your result, but it does not tell you the result.

Done when
  • With \(K = 1\) your rule gives the conventional switch again.
  • The wavelength of a connection does not depend on the wavelength-routing switch that carries it. A rearrangement (an existing connection moves to another wavelength-routing switch of the middle stage, page 11) then never changes the wavelength of a transmitter.
  • With concentrated traffic the crosstalk advantage of the proposed switch is gone. Crosstalk is the disturbance that the leaks cause.
  • An aggregation coupler (the coupler that combines the signals in front of an EDFA) never carries two signals of the same wavelength.
  • Your code gives the same numbers as your small example that you checked by hand.
Bring to your supervisor

Before you write code: a plan of one page with your wavelength rule, a small example drawn by hand, your two traffic definitions and the list of the figures that you intend to produce. At the end of the phase: the rule, the definitions and the table of leak counts.

Structure

Both prior papers have six sections in the same order: introduction, earlier switch architectures, proposed switch, simulation, experiment, conclusion. A short conference paper can keep this order in much less space. The introduction on page 01 is a first draft, and it already covers the earlier switches. Four parts remain to be written:

  1. the proposed switch: its structure and its wavelength rule (phase 4);
  2. the simulation: the model, the common parameter set and the comparison of the three switches (phases 1 to 3, 5 and 6);
  3. the experiment (phase 7);
  4. the conclusion: the answer to the question of the introduction, with numbers.

Take the page limit and the template from the call for papers of the conference.

12. Good practice

The rules of this section keep your results reproducible. A result is reproducible when you, or another person, can produce exactly the same numbers again at a later time. The section extends the working rules of Start here.

Results

  • One folder for results. The two main scripts write into matlab/results/. Every run writes new files, and each file name carries the time of the run, so a run never overwrites an earlier one. Do the same in your own scripts.
  • Parameters and seed with every result. The .mat file of a main script holds all parameters, the seed and all results. A result without its parameters cannot be reproduced, so it cannot go into the paper.
  • One script per figure. For every figure that you show to another person, keep one script that loads a result file and draws the figure. You can then change a label without running the simulation again, and you always know which data are behind the figure.
  • No number edited by hand. Not in a result file, not in a table, not in a figure. If a number is wrong, correct the script and run it again.
  • The given code stays as it is. Do not edit the folder lib. In a demo script or a script of matlab/main/, change only the parameter values that a page or the header of the script asks you to try, and set them back afterwards. For every other change, copy the script into matlab/work/ under a new name and change the copy. When you doubt the library, run run_all_tests: it must end with All tests passed.

Notebook

  • Keep a notebook, on paper or in a file. For every run that you keep, write down the name of the result file, what you changed, why you changed it, what you expected and what came out.
  • Change one thing at a time, and write down your prediction before you run.

Before you believe a result

  • Check a limit case. A limit case is a case whose answer you know before you run it. Two examples: \(K = 1\), which must give the conventional switch; an operating point that a given script already computes.
  • One run near the FEC limit does not decide. A BER is counted from a finite number of bit errors, so it has a random error: about 30 percent of its value for 10 counted errors and about 4 percent for 700 (see the comments in step21_two_stage_one_point).

When you are stuck

  1. Reduce the problem to one operating point. A search over many operating points hides what happens inside one of them. The main scripts set the seed before every operating point. The step script with the same parameters, the same datasize and the same seed therefore prints the same BER as the search.
  2. Plot the level diagram with plot_level_diagram(stage_names, stage_power), as the step scripts do. Find the first block after which the power is not what you expect.
  3. Compare with the hand budget. Calculate the power after every block and the SNR contributions with formulas, as sections 5 and 6 of the step scripts do. The first block at which simulation and budget disagree is the place to look. The error is in the code or in the budget.
  4. Go back to a case that worked. Undo your changes one at a time until the result of the given script returns.
  5. Ask. If you are still stuck, go to your supervisor with the one operating point, the two tables and a list of what you tried.
Key idea

Find your phase on this page, and read its "Done when" list: it tells you what is still missing. In phases 0 to 3 you learn to run and to explain the given material. Phases 4 to 6 are your own work: no answer is given, and consistency conditions test your result instead. Every figure of the paper must lead back to a saved result with its parameters and its seed.
